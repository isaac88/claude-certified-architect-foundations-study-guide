# 4.2 Few-shot prompting

Few-shot is the most effective lever for **consistency**. Not a longer instruction block. Not a confidence threshold.

## When to deploy

- Detailed instructions still produce **inconsistent formatting**
- The model **flip-flops on ambiguous** cases (flag vs skip)
- Extraction leaves **empty/null** on fields that **are** in the document (layout variance, not absence)

## How to construct

- **2–4** targeted examples, not a novel
- Each example includes **reasoning**: why this action beat a plausible alternative (“not a bug: this is the framework’s required empty catch”)
- That reasoning is what generalises to **novel** patterns. Bare input/output pairs only teach the pre-specified cases

Cover the borders: skip vs flag, two document layouts, an `other` / refuse example.

## Hallucination and layout

Extraction quality jumps when examples show **varied structures**:

- Inline citations vs bibliography blocks
- Narrative paragraphs vs tables

The model copies the *handling strategy*, not just the field names. If invoices in the wild mix tables and prose, your four examples must too.

## What few-shot is not

- Not the **first** fix for overlapping tool descriptions (2.1 — expand descriptions)
- Not a substitute for a refund **gate** (1.4)
- Not a JSON **guarantee** (4.3 — `tool_use`)

## Practice

Instructions for review output format are a page long; every PR looks different. Ambiguous “is this a bug?” calls go both ways.

**Deploy 2–4 few-shot examples** with reasoning for format *and* for a borderline skip/flag. Do not add a fifth page of rules. Do not add “only high confidence”.

## Check questions

1. Extraction returns null `total` but the PDF table has a total. Instructions look complete. What do you add first?
2. Why include reasoning in the example, not only the final JSON?

## Connects to 4.3

Few-shot improves judgement. It does not stop `{ "total":` with a missing brace. Shape needs `tool_use`.
