# 4.4 Validation-retry loops

## Retry with error feedback

Send back **all three**:

1. Original document  
2. Failed extraction  
3. **Specific** validation error (field, expected vs actual)

“There was an error, try again” does not tell the model what to fix.

## When retry works vs when it does not

| Retry **effective** | Retry **ineffective** |
|---|---|
| Format mismatch (date `31/12/24` vs ISO) | Field **genuinely absent** from the source |
| Structural leftover the schema did not catch | You required a field that should have been nullable (fix the **schema**, do not retry forever) |
| Value in the wrong field but present in the doc | Asking the model to invent a PO number that is not on the page |

The exam will show both. If the stem says the document never mentions X, the answer is **null / `other` / stop**, not another retry.

## `detected_pattern` (and friends)

Add a field that records **which construct** triggered a finding (`detected_pattern: "empty_catch"`). When developers dismiss findings, you can tally patterns and **fix prompts with data**, not anecdotes.

## Self-correction in the schema

- Extract `stated_total` **and** `calculated_total` so mismatches are first-class.
- `conflict_detected: true` when sources in the same document disagree.

Do not hide the conflict by picking one number.

## Practice

Validation: line items sum to 90, `stated_total` is 100. Document clearly shows both.

**Retry** with: original PDF/text, the JSON, “calculated_total 90 ≠ stated_total 100; extract both and set conflict_detected”.

Same validator, but the scan is a photo of a blank “PO number” box.

**Do not retry** for a PO. Schema should allow null; return null.

## Check questions

## Connects to 4.5

Once the prompt+schema+retry works on a **sample**, you may batch the rest. Do not batch first.
