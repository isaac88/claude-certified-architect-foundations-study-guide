# 4.1 Explicit criteria

Vague confidence talk does not calibrate a reviewer. **Specific categorical criteria** do.

**Wrong**

- “Be conservative.”
- “Only report high-confidence findings.”
- “Check comments are accurate.”

**Right**

- “Flag comments **only** when claimed behaviour contradicts actual code.”
- “Report bugs and security vulnerabilities.”
- “Skip minor style preferences and local patterns.”

The model can follow a category. It cannot reliably implement “conservative”.

## False positives destroy all categories

If one noisy category (for example comment nits) floods the PR, developers ignore **security** findings too. Trust is global.

**Fix:** temporarily **disable** the noisy category while you sharpen that prompt. Keep the trustworthy categories live. Restore the noisy one only when its precision is acceptable.

Do not “add more comments but ask it to be careful”. That is still the broken category.

## Severity calibration

Do not define “critical” in adjectives. Give **concrete code examples** for each severity:

- Critical: unsanitised query concatenated from request params (show a 4-line snippet).
- Minor: unused import in a test helper (show a snippet).

Prose (“critical means it could cause outage”) still leaves a judgement gap. Examples close it.

## Practice

CI review flags 40 style nits and 2 real bugs. Developers start dismissing everything.

**First move:** turn off the style category; keep bug/security rules; rewrite style criteria with examples before re-enabling.

Not: raise a confidence threshold. Not: “be more conservative.”

## Check questions

1. Why does disabling one category restore trust in the others?
2. What is missing if severity is only described as “high / medium / low”?

## Connects to 4.2

Criteria say *what* to flag. Few-shot examples teach *borderline* cases and output shape.
