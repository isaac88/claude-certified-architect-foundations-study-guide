# 4.3 Structured output with `tool_use`

## Reliability hierarchy

| Method | Syntax (valid JSON) | Semantics (correct values) |
|---|---|---|
| “Output as JSON” in the prompt | Not guaranteed | Not guaranteed |
| Regex / repair after the fact | Fragile | Fragile |
| **`tool_use` + JSON Schema + `tool_choice`** | **Eliminates syntax errors** | **Not guaranteed** |

Read fields from the `tool_use` input. Do not parse assistant prose.

## What `tool_use` does **not** prevent

- Line items that **do not sum** to `stated_total`
- Values in the **wrong fields** (date in invoice number)
- **Fabrication** when a required field is missing from the source

Schema-valid ≠ correct. The exam will offer “the schema matched so the data is right”. Reject it.

## `tool_choice` (same table as 2.3, extraction angle)

| Value | Use in this domain |
|---|---|
| `"auto"` | Model may chat instead of extracting — **wrong** when you must have a record |
| `"any"` | Must call *a* tool; picks which — **unknown document type**, several schemas |
| `{"type": "tool", "name": "extract_invoice"}` | Must call **that** tool — known type, or mandatory first extractor |

## Schema design that prevents fabrication

- **Optional / nullable** fields when the source may not contain the value. Required fields on sparse documents **force invention**.
- Enum includes **`unclear`** for ambiguous classification.
- **`other` + freeform detail** for types you did not enumerate (unknown document class).
- Put **format normalisation** (dates → ISO) in the prompt **alongside** the schema. The schema enforces types; the prompt says how to coerce.

## Practice

Downstream parser requires JSON. Prompt says “respond only with JSON”. Occasional parse failures.

**Guarantee:** extraction tool with JSON Schema, `tool_choice` `"any"` or forced name.

Parser then succeeds; totals still wrong. That is **4.4**, not a reason to drop `tool_use`.
