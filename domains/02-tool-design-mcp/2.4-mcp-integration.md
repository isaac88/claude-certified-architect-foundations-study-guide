# 2.4 MCP server integration

MCP (Model Context Protocol) is how you plug external tools and resources into Claude Code and agents. The exam cares about **where the config lives**, **how secrets are injected**, and **whether you needed to build anything**.

## Scoping hierarchy

| Scope | File | Shared? Version-controlled? |
|---|---|---|
| **Project** | `.mcp.json` in the repo | Yes. Whole team after clone/pull |
| **User** | `~/.claude.json` (Claude Code user config) | No. That machine only |

Team Jira/GitHub/Slack → **project** `.mcp.json`.  
Personal scratch server → user config.

All tools from **all** configured servers are discovered at connection time and sit in the same pool. That is why 2.3 still applies: a project with six MCP servers can dump 40 tools on one agent. Scope servers *and* `allowedTools`.

## Environment variable expansion

`.mcp.json` supports `${GITHUB_TOKEN}` (and the same pattern for other secrets).

- Commit the config.
- Each developer (and CI) sets the variable locally.
- **Never** commit the token.

Hardcoded keys in `.mcp.json` is an automatic wrong answer.

## MCP resources

Servers can expose **resources**: catalogues, not just tools.

Examples: issue summaries, doc trees, database schemas.

The agent **sees what exists** without a fishing expedition of list/search calls. Use resources to cut exploratory tool use. If the agent is calling `list_issues` twenty times to learn the project, you probably wanted a resource.

## Build vs use

| Need | Move |
|---|---|
| Jira, GitHub, Slack, similar | Evaluate **community MCP servers** first |
| Team-specific workflow the community server cannot express | Then build custom |
| Agent prefers `Grep` over your MCP code-search | **Enhance the MCP tool description** (2.1), do not ban Grep in a prompt as the first fix |

Custom Jira “because we can” fails the low-effort rule. Custom is justified when: auth model, required fields, or workflow states are unique and a community server cannot map them without fiction.

## Practice scenario

The team needs Jira. One engineer starts a custom MCP server.

**Why evaluate community first?** Standard issue tracker. Existing servers already handle auth, pagination, and tool descriptions. Custom is weeks of undifferentiated work and another tool-description surface to get wrong.

**When is custom justified?** Internal Jira-like system, mandatory custom fields the community server cannot send, or a workflow (CAB, freeze windows) that a generic server will mis-model.

## Check questions

1. New hire cannot see the GitHub MCP tools everyone else uses. Where do you look first?
2. Agent uses `Grep` instead of the GitHub MCP search that would hit PRs and issues. First fix?

## Connects to 2.5

Built-in tools compete with MCP tools in the same pool. You must know which built-in to pick, and never use Bash as a substitute.
