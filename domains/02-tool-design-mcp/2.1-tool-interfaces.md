# 2.1 Tool interface design

Tool **descriptions** are not documentation for humans. They are **the primary mechanism** Claude uses to choose a tool. Not a hint. Not supplementary. If two tools both say “Retrieves [entity] information”, the model is guessing.

## Production picture — support desk

Tools: `get_customer`, `lookup_order`.

Customer: *“Check the status of order #12345.”*

If descriptions are:

- `get_customer`: “Retrieves customer information.”
- `lookup_order`: “Retrieves order information.”

both accept string identifiers, and the system prompt says “always look up the customer”, the agent will call `get_customer` with `"#12345"`. Wrong tool. Wrong backend. Sometimes a wrong refund later (Domain 1.4 still needs a gate; this task is why the *first* call was wrong).

## What a good description contains

Every tool description on the exam should be able to answer these:

1. **Primary purpose** — what it does in one precise sentence.
2. **Inputs** — formats, types, constraints (`ORD-12345` vs UUID vs email).
3. **Example queries it handles well** — the utterances that should select it.
4. **Edge cases and limits** — guest checkout, missing order, name-only lookup.
5. **Explicit boundaries** — when to use **this** tool versus its siblings.

Example shape (not magic wording — the *distinctions* are what matter):

```
lookup_order: Look up a sales order by order number (format ORD-##### or #12345).
Use when the user quotes an order id, tracking number, or asks about shipping
status, items, or delivery. Do NOT use for account profile, email, or identity
verification — that is get_customer. Guest orders are supported. Returns 200
with an empty order object only when the id is well-formed and no order exists.
```

```
get_customer: Load a customer record by customer UUID or verified email.
Use when you need identity, addresses, or payment methods on file.
Do NOT use when the user has supplied an order number — that is lookup_order.
```

## Misrouting (exam Q2 pattern)

**Symptom:** constant mix-ups between similar tools.  
**Root cause:** minimal, overlapping descriptions.  
**First fix:** expand descriptions.

| Option | Why it is wrong as the *first* step |
|---|---|
| Few-shot examples of correct routing | Token overhead; does not fix the selection signal |
| Routing classifier / keyword layer | Over-engineered; bypasses the model’s job |
| Merge into `lookup_entity` | Heavy rewrite; hides two backends behind one contract |
| **Expand descriptions** | Hits the actual mechanism; cheap; reversible |

After descriptions are sharp, if overlap remains, **split or rename**. Do not start with merge.

## Tool splitting

Generic tools invite generic calls. Split by **job and contract**, not by backend.

`analyze_document` →

- `extract_data_points` — structured fields, schema-shaped
- `summarize_content` — prose summary, no citations required
- `verify_claim_against_source` — one claim in, pass/fail + quote out

A synthesis agent can hold `verify_claim_against_source` without inheriting the whole document toolkit (that is 2.3).

## System prompt vs descriptions

Keyword-sensitive instructions **override** good descriptions.

- “Always look up the customer” → `get_customer` on every turn, including order-number queries.
- “Search thoroughly” → MCP search ignored in favour of a dozen `Grep`s.

After you change descriptions, **re-read the system prompt** for colliding keywords. Fix both, or the prompt will win.

## Practice scenario

Agent routes “check the status of order #12345” to `get_customer`. Both descriptions: “Retrieves [entity] information.”

**A)** Add 5–8 few-shot traces of order queries going to `lookup_order`.  
**B)** Expand each description with inputs, examples, edge cases, and an explicit boundary.  
**C)** Add a pre-router that regexes `#\d+` and disables `get_customer`.  
**D)** Merge into `lookup_entity`.

**Answer: B.** Root cause is the selection signal. A treats a prompt bandage as a contract fix. C and D are disproportionate first steps.
