# 2.2 Structured error responses

The model can only recover from what you tell it. `"Operation failed"` forces a coin-flip: retry, escalate, or invent.

MCP uses **`isError: true`** when the tool actually failed. Pair it with metadata the coordinator (or the same agent) can branch on.

## Four error categories

| Category | Examples | Retry? | Next move |
|---|---|---|---|
| **Transient** | Timeout, 503, rate limit | Yes | Backoff, then retry; then propagate if still dead |
| **Validation** | Bad format, missing required field | After fixing input | Ask the user or correct the argument; then retry |
| **Business** | Refund over policy limit, duplicate payout | **No** | Alternative workflow (escalate, split refund, refuse). `isRetryable: false` |
| **Permission** | 401/403, missing scope | No (same credentials) | Escalate or obtain different credentials |

Minimum payload:

- `isError`
- `errorCategory` (those four distinctions — names may vary; the behaviour must not)
- `isRetryable` / `retriable`
- Human-readable description the agent can show a customer on **business** errors (“This refund exceeds the £500 self-serve limit; I can escalate.”)
- What was attempted; partial results if any

Business errors need `retriable: false` **and** a customer-safe explanation. Silent `false` with no text makes the agent invent a reason.

## Access failure vs valid empty result

This is the Domain 2 distinction the exam loves.

| | Access failure | Valid empty result |
|---|---|---|
| Did the query run? | No (timeout, auth, network) | Yes |
| `isError` | `true` | `false` |
| Body | Error metadata | Empty list / null record, success |
| Agent should | Decide retry vs escalate | **Not** retry. The answer is “no match” |

If you return `[]` on a timeout, the agent concludes the customer does not exist, or it retries a successful empty lookup forever, or it escalates a non-problem.

If you set `isError: true` on “account not found”, the agent retries a lookup that will never succeed.

## Propagation in multi-agent systems (ties to 1.2 / 5.3)

- Spokes **retry transient** errors locally (short backoff).
- Propagate only what they **cannot** fix.
- Include: failure type, attempted queries, **partial results**, suggested alternatives.
- Do not swallow the error as empty success. Do not explode the whole research job.

## Practice scenario

`get_customer("Ada Lovelace")` returns `[]`. The agent retries three times, then escalates to a human. The account does not exist. Lookups are fast and 200.

**Problem:** the tool (or the agent’s interpreter) treated a **valid empty result** as an **access failure**. Retries cannot create an account. Escalation wastes a human on “we have no Ada Lovelace”.

**Fix:** successful empty payload, `isError: false`. Agent tells the user no account matched and asks for another identifier (email, customer ID) — Domain 5.2 ambiguity, not a pager incident. Reserve retries for transient `isError`.

## Check questions

1. Refund tool returns “amount exceeds policy”. Retryable? What should the agent do instead?
2. Search subagent times out after one useful snippet. What belongs in the payload to the coordinator?

## Connects to 2.3

Errors and descriptions assume the **right agent** has the **right tools**. Eighteen tools on one agent, or a synthesis agent with the whole web, undoes both.
