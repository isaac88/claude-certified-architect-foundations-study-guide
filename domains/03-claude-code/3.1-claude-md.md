# 3.1 CLAUDE.md hierarchy

Claude Code loads memory from three layers. The exam’s favourite bug is putting **team law** in the **personal** layer.

## Three levels

| Level | Typical path | Who gets it? | Git? |
|---|---|---|---|
| **User** | `~/.claude/CLAUDE.md` | Only you, on that machine | No |
| **Project** | `.claude/CLAUDE.md` or repo-root `CLAUDE.md` | Everyone who clones/pulls | Yes |
| **Directory** | `CLAUDE.md` inside a subdirectory | When work is in that tree | Yes |

User-level is for personal taste (how *you* like commit messages). It is **not** the team API naming guide.

A new teammate clones the repo and Claude ignores your conventions → look at **user-level** first. Developer A’s `~/.claude/CLAUDE.md` is invisible to Developer B.

## Modular organisation

One 2,000-line CLAUDE.md wastes tokens and hides the rule you need.

- **`@import`** from CLAUDE.md to pull package-specific standards (`@docs/standards/payments.md`) so each package loads what it needs.
- **`.claude/rules/`** for topic files (`testing.md`, `api-conventions.md`, `deployment.md`) instead of one blob. Path-scoped rules (3.3) live here too.

## `/memory`

Debugging tool. Shows **which memory files are actually loaded** this session. Use it when:

- Two developers see different behaviour on the same repo
- A rule you wrote “isn’t applying”
- You are unsure whether user-level is leaking in

Do not guess. Run `/memory`.

## Practice scenario

Developer A’s Claude follows the team API naming conventions. Developer B joined last week; naming is inconsistent. Same repo, same branch.

| Option | Verdict |
|---|---|
| **A. Instructions live in A’s `~/.claude/CLAUDE.md`** | **Correct.** B never received them. Move to project `.claude/CLAUDE.md`. |
| B. B needs a bigger model | Distractor. Not a model-size problem. |
| C. B forgot to run `/review` | Commands are not how universal standards load. |
| D. Add the conventions to a personal skill on B’s laptop | Still not shared; next hire fails too. |

## When rules collide — and what actually enforces

*(Added 21 Sep 2026 after a mock exposed this gap; wording sourced from the vendor's memory docs.)*

The three levels do **not** override each other. The docs' own words:

- All discovered files are “**concatenated into context rather than overriding each other**”, listed in load order from broadest scope to most specific — so a project instruction appears in context *after* a user instruction. Load order is **reading order, not precedence**.
- “**If two rules contradict each other, Claude may pick one arbitrarily.**” The fix for a contradiction is to *remove it*, not to move a rule to a “stronger” memory file.
- CLAUDE.md is “**context, not enforced configuration**. To block an action regardless of what Claude decides, use a PreToolUse hook instead.”

“The more specific scope wins” is folk knowledge and a named exam distractor.

**`CLAUDE.local.md`**: personal per-project preferences, gitignored, appended after `CLAUDE.md` within its directory. Being read last still does not make it win a contradiction.

**The enforcement ladder** — where a rule can live, by how hard it binds:

| Layer | Binding | Use for |
|---|---|---|
| CLAUDE.md / `.claude/rules/` | Guidance — probabilistic | Conventions, style, context |
| `settings.json` permissions | Client-enforced | Allowing/denying tools and commands |
| Hooks (PreToolUse, PostToolUse, …) | Client-enforced, applied regardless of what the model decides | Rules that must hold every time: money, security, format-on-save |

A team rule that **must hold on every run** therefore lives in settings or a hook; CLAUDE.md carries the same rule as context so the model also *understands* it.

The two enforcement layers are not interchangeable — an exam answer that names "settings/hooks" as one thing is half an answer:

- **`settings.json` permission rules** — a **static pattern on the tool call text** (`Bash(git push:*)`, `Edit(src/**)`), evaluated before the call; **deny > ask > allow**. Cannot look at anything outside the call itself.
- **Hooks** — a **script that runs at a lifecycle event** and can read state the pattern cannot (current branch, file contents, time, a lint result); a PreToolUse hook blocks with exit 2.

## Hook events — the catalogue

*(Added 23 Sep 2026 from the vendor hooks reference. Mocks taught four events; the reference lists over thirty.)*

Hooks fire on **lifecycle events**, not only on tools. The exam's favourite trap is to offer a `PreToolUse` hook for something that is not a tool call — compaction, session start, a prompt being submitted.

| Group | Events | Exam tell |
|---|---|---|
| Session | `SessionStart`, `Setup` (`--init`/`--maintenance`), `Stop`, `StopFailure` | Inject context at start (`SessionStart` stdout becomes context Claude sees); `Stop` exit 2 keeps Claude working |
| Prompt | `UserPromptSubmit`, `UserPromptExpansion` | Validate or block a prompt **before** Claude sees it (exit 2 erases it) |
| Tool | `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch` | **Pre** touches the input before execution (block/validate); **Post** touches the result after (normalise/format) — a file must exist to be formatted → Post |
| Compaction | `PreCompact`, `PostCompact` | Compaction is a **lifecycle operation, not a tool** — `PreToolUse` can never see it |
| Agents | `SubagentStart`, `SubagentStop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted` | Audit or gate delegation |
| Worktree | `WorktreeCreate`, `WorktreeRemove` | Replace the git logic (non-git VCS); any non-zero exit aborts creation |
| Config / environment | `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `PreModelSwitch`, `PostModelSwitch` | Know when a CLAUDE.md or rule file actually loaded |
| MCP / UI | `Elicitation`, `ElicitationResult`, `Notification`, `MessageDisplay` | — |

**Exit codes** (vendor wording):

- **0** — success. Stdout is parsed as JSON for structured control when it starts with `{` and ends with `}`; otherwise plain text. Plain stdout is shown to Claude as context only for `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart` and `PostModelSwitch`; for other events it goes to the debug log.
- **2** — **blocking error** on the events that can block: `PreToolUse` blocks the call, `UserPromptSubmit` blocks and erases the prompt, `Stop` prevents stopping, `PreModelSwitch` blocks the switch. Exit 2 blocks even if the JSON says allow. **`PermissionRequest` does not honour exit 2** — deny through the `decision` object instead.
- **Any other non-zero** — does **not** block on its own; the action proceeds and a non-blocking hook error is shown. This is the fail-open row in the ledger: a hook that crashes with exit 1 lets the call through. A money or destructive guard must therefore exit 2 explicitly on every failure path, including its own errors.

## Check questions

1. Where do testing standards the whole team must follow live?
2. Claude “ignores” a rule you added yesterday. First debugging command?
3. Project CLAUDE.md says 4-space indent; a teammate’s `~/.claude/CLAUDE.md` says 2-space, and builds are breaking. What does Claude Code actually do with the two rules, and name **both** places the team rule goes if it must hold on every save.
4. A teammate proposes moving the team rule into `CLAUDE.local.md` “because it loads last”. Two reasons that fails.
