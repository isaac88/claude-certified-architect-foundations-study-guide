# 3.2 Custom slash commands and skills

## Directories

| What | Team (shared, git) | Personal (not shared) |
|---|---|---|
| Slash commands | `.claude/commands/` | `~/.claude/commands/` |
| Skills (`SKILL.md`) | `.claude/skills/` | `~/.claude/skills/` |

`/review` for everyone after clone → **project** `.claude/commands/`.

CLAUDE.md is not a command registry. A `commands` array in `.claude/config.json` is a distractor — that mechanism is not how Claude Code registers slash commands.

## Skills vs CLAUDE.md vs commands

| | When it loads | What it is for |
|---|---|---|
| **CLAUDE.md / rules** | Always (or path-scoped — 3.3) | Universal standards |
| **Slash command** | When the human types `/name` | Repeatable team ritual (`/review`, `/test`) |
| **Skill** | On-demand when invoked / matched | Task-specific workflow with **frontmatter** |

Do **not** put “how we name REST resources” in a skill (people will forget to invoke it).  
Do **not** put a 400-line exploratory refactor procedure in CLAUDE.md (it pollutes every session).

Personal variants: `~/.claude/skills/` with a **different name** so you do not clobber the team skill.

## Skill frontmatter

- **`context: fork`** — isolated sub-agent. Verbose analysis/brainstorm stays out of the main thread. Use for codebase mapping, noisy brainstorms, anything that would drown the parent.
- **`allowed-tools`** — lock the skill to Read/Grep/Glob (or similar) so it cannot `Write` production code while “just looking”.
- **`argument-hint`** — if invoked with no args, prompt for the required parameter (PR number, module path).

## Practice scenario

The team wants `/review` for everyone. One developer also wants a personal `/brainstorm` (or brainstorm skill) that dumps verbose output.

| Artefact | Where | Config |
|---|---|---|
| `/review` | `.claude/commands/` in the **repo** | Shared markdown command body; no fork required if the output is the review itself |
| Personal verbose brainstorm | `~/.claude/skills/` (or `~/.claude/commands/`) **not** the repo | Skill: `context: fork` so the dump stays isolated; `allowed-tools` read-only if it must not edit; unique name so it does not override team skills |

Putting `/review` in `~/.claude/commands/` means new hires do not get it (same trap as 3.1). Putting brainstorm in project skills without fork pollutes every teammate’s main session when they invoke it.

## Check questions

1. Why is “add the review checklist to CLAUDE.md” the wrong place for a `/review` ritual?
2. When must a skill set `context: fork`?

## Connects to 3.3

Always-on rules that should apply only to **some files** are not skills and not a root CLAUDE.md dump. They are path-specific rules.
