# 3.2 Custom slash commands and skills

## Directories

| What | Team (shared, git) | Personal (not shared) |
|---|---|---|
| Slash commands | `.claude/commands/` | `~/.claude/commands/` |
| Skills (`SKILL.md`) | `.claude/skills/` | `~/.claude/skills/` |

`/review` for everyone after clone → **project** `.claude/commands/`.

CLAUDE.md is not a command registry. A `commands` array in `.claude/config.json` is a distractor — that mechanism is not how Claude Code registers slash commands.

## Skills vs CLAUDE.md vs commands

| | When it loads | What it is for |
|---|---|---|
| **CLAUDE.md / rules** | Always (or path-scoped — 3.3) | Universal standards |
| **Slash command** | When the human types `/name` | Repeatable team ritual (`/review`, `/test`) |
| **Skill** | On-demand when invoked / matched | Task-specific workflow with **frontmatter** |

Do **not** put "how we name REST resources" in a skill (people will forget to invoke it).
Do **not** put a 400-line exploratory refactor procedure in CLAUDE.md (it pollutes every session).

Personal variants: `~/.claude/skills/` with a **different name** so you do not clobber the team skill.

## Skill frontmatter — what each field actually does

Sourced from the vendor skills and sub-agents docs, fetched 23 Sep 2026. Earlier versions of this note taught two of these wrong; the corrections are marked.

- **`context: fork`** — runs the skill in a **new subagent** (type set by the `agent` field) with the skill content as its prompt. The subagent **does not see your conversation history**, so the skill's instructions must stand on their own. What it buys you: the skill's reading and working stay in the child's window, and only the result comes back — the **parent's** window is protected. Vendor: "Despite the name, a skill with `context: fork` doesn't run in a fork of the current conversation, which would hand the subagent everything you've discussed so far. When the task depends on that history, fork the conversation instead of using `context: fork`." Use for codebase mapping, noisy brainstorms, long audits — anything that would drown the parent and needs nothing from the chat so far. A fresh context costs more than running inline.
  ⚠ **Correction (23 Sep 2026):** this note used to say the forked skill inherits the conversation. It does not. The mechanism that inherits is the fork *subagent*, below.
- **`allowed-tools`** — a **pre-approval grant, not a fence**. The listed tools run **without a permission prompt during the turn that invokes the skill**; the grant clears when you send your next message. Vendor: "It does not restrict which tools are available: every tool remains callable, and your permission settings still govern tools that are not listed." For a whole-session pre-approval use allow rules in permission settings instead.
  ⚠ **Correction (23 Sep 2026):** this note used to say "lock the skill to Read/Grep/Glob so it cannot Write". `allowed-tools` cannot lock anything.
- **`disallowed-tools`** — tools **removed from Claude's available pool while the skill is active**; also clears on your next message. For autonomous skills that must never call, say, `AskUserQuestion`.
- **`argument-hint`** — if invoked with no args, prompt for the required parameter (PR number, module path).

## Tool access: the enforcement ladder

| Layer | Scope | What it does | Guarantee? |
|---|---|---|---|
| `allowed-tools` (skill) | The invoking turn | Pre-approves the listed tools — no prompt | No — a grant |
| `disallowed-tools` (skill) | The invoking turn | Removes the listed tools from the pool | Only for that turn |
| Permission rules in `settings.json` | Session / project / org | Static pattern on the tool call; **deny > ask > allow** | Yes |
| `PreToolUse` hook | Every tool call, every session | Runtime logic on the call; exit 2 blocks | Yes |

Exam tells. "The skill keeps pausing for approval on its own tools" → `allowed-tools` (grant side). "Guarantee the skill can **never** run Bash" → a **deny rule** in settings or a PreToolUse hook — never `allowed-tools`. The two-line answer the enforcement pair needs: the permission rule is a static pattern on the call text; the hook is runtime logic (branch state, file path, time) that can block with exit 2.

## Four things called "fork", and the one that is not

| Mechanism | What it is | Carries the conversation? | Isolates what |
|---|---|---|---|
| `context: fork` (skill frontmatter) | Skill content runs as the prompt of a fresh subagent | **No** | The parent's context window |
| Fork subagent (`subagent_type: fork`, "fork the current conversation") | A subagent that starts as a **copy** of the conversation: full history, the main conversation's exact tool pool, output style and model | **Yes** | The parent's window from the child's working; writes stay on the copy |
| `/fork` (slash command) | Copies the conversation into a **new background session** while you keep working | **Yes** | Nothing about files — a second session |
| `--fork-session` (CLI flag, with `--resume` or `--continue`) | Resume a saved session as a new session id, original untouched (1.7) | **Yes** | The original transcript |
| **`git worktree`** (`--worktree <name>`, `EnterWorktree`, subagent `isolation: worktree`) | A separate working directory with its own files and **branch**, sharing the repository history | Not a context mechanism | **File edits** — one session's edits never touch another's |

Decision rules:

1. **Does the child need what was said this session?** Yes → fork subagent. No → `context: fork` skill or a plain subagent (blank page). Both keep the child's working out of the parent's window.
2. **Several agents editing files at once?** → **worktree**. A fork copies *context*, not the file system; two forks in one checkout collide on the same files. Vendor: worktrees "isolate file edits", subagents "split work up inside one session".
3. **Compare two approaches from one analysis, later, from a saved session?** → `--fork-session`.
4. Cleanup: a subagent's worktree is removed automatically when it finishes without changes; one with changes stays until the periodic sweep.

Exam-guide note. The exam guide is v1.0, July 2026. The fork subagent became the default "fork mode" in mid-August 2026 (vendor what's-new, week 33), so the exam's `context: fork` items were written when the only fork on a skill was the isolated, no-history kind — which is exactly what the current doc still says. Third-party keys ("isolated subagent context, returns results") agree. If a stem says the skill *knew* session details, that is the fork subagent, not `context: fork`.

## Practice scenario

The team wants `/review` for everyone. One developer also wants a personal `/brainstorm` (or brainstorm skill) that dumps verbose output.

| Artefact | Where | Config |
|---|---|---|
| `/review` | `.claude/commands/` in the **repo** | Shared markdown command body; no fork required if the output is the review itself |
| Personal verbose brainstorm | `~/.claude/skills/` (or `~/.claude/commands/`) **not** the repo | Skill: `context: fork` so the dump stays isolated — the brainstorm needs no chat history; `disallowed-tools: Write, Edit` for that turn if it must not edit, or a deny rule in settings for a real guarantee; unique name so it does not override team skills |

Putting `/review` in `~/.claude/commands/` means new hires do not get it (same trap as 3.1). Putting brainstorm in project skills without fork pollutes every teammate's main session when they invoke it.

## Check questions

1. Why is "add the review checklist to CLAUDE.md" the wrong place for a `/review` ritual?
2. A skill must summarise what was already discussed this session, and its long output must stay out of the main window. `context: fork` or the fork subagent — and which property decides?
3. Three agents must edit three services' files at the same time. Which mechanism, and what does a fork not provide?
4. "Guarantee this skill never runs Bash." Which field or location, and why is `allowed-tools` the wrong answer?

## Connects to 3.3

Always-on rules that should apply only to **some files** are not skills and not a root CLAUDE.md dump. They are path-specific rules.
