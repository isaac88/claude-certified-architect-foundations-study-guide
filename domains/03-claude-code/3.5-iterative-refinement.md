# 3.5 Iterative refinement

Vague “make it better” is not a technique. The exam ranks methods by how much **unambiguous signal** you give.

## Technique hierarchy (try in this order)

1. **Concrete input/output examples (2–3 before/after pairs).** Beats a page of prose. The model generalises from examples more reliably than from descriptions. If Claude interprets a transformation differently each run, **switch to examples first** — not a longer essay.
2. **Test-driven iteration.** Write failing tests (or share the failure output). Implement until green. Keep tests green while refining.
3. **Interview pattern.** Ask Claude to **question you** before coding when the domain is unfamiliar. Surfaces constraints you would omit from a spec.

## Batch vs sequence

| Feedback | How to send it |
|---|---|
| Fixes **interact** (changing A breaks B) | **One message** with all of them |
| Issues are **independent** | Sequential iteration is fine |

Dumping twelve interacting nits one at a time produces a moving target. Dumping twelve independent nits in one blob is fine if they do not collide.

## Practice scenario

A developer describes a code transformation in prose. Claude Code implements a different interpretation each time.

**First technique:** 2–3 concrete input/output examples of the expected transformation.

**Why:** Prose is under-specified; examples pin the mapping. Longer prose usually adds more ambiguity. TDD is excellent **once** you can write tests for the mapping; examples are the cheaper first move when even the expected output is unclear. Interview pattern is for unknown domains, not for a transformation you can already show.
