# 1.6 Task decomposition strategies

Two patterns. The exam tells you which one to pick by whether the **structure is known in advance**.

## Fixed sequential pipelines (prompt chaining)

Break work into predetermined steps. Output of step *n* is input to step *n+1*.

**When:** workflow is known, steps are stable, outputs feed the next stage consistently.

**Example — code review of a 14-file PR:**

1. **Per-file local pass** (parallelisable): logic, security, error handling, line-level findings.
2. **Cross-file integration pass** (after all local results): interface mismatches, duplicated logic, cycles.
3. **Summary:** severity-ordered comment list.

This is also how you fight **attention dilution**: one prompt over 14 files produces patchy comments. Split the job.

Sample-exam shape: a single-pass review of 14 files is inconsistent → per-file then integration, not “buy a bigger context window”.

## Dynamic adaptive decomposition

Generate subtasks from what you discover. The plan can change.

**When:** you cannot know the subtasks up front (legacy investigation, “add tests where it matters”).

**Example — tests for a legacy codebase:**

1. **Map structure** (no tests yet): modules, existing coverage, frameworks, high-risk files.
2. **Prioritise:** critical path with zero coverage, high complexity, I/O boundaries.
3. **Execute adaptively:** when `payment_processor` tests reveal that `config_loader` must be mocked first, rewrite the queue before continuing.

Skipping the map causes duplicate work and wrong priorities.

## How to choose

| Signal in the stem | Pattern |
|---|---|
| “Review each file, then summarise” | Prompt chaining |
| “Unfamiliar legacy codebase, coverage where it matters” | Adaptive |
| Plan mode vs direct execution (Domain 3) | Plan ≈ adaptive map; direct ≈ known small edit |

Do not use adaptive decomposition for a well-defined pipeline — extra latency for no gain. Do not freeze a pipeline that must react to discoveries.

## Anti-patterns

- All files in one review prompt (attention dilution)
- Adaptive machinery on a known three-step review
- Skip structure-mapping on open-ended work
- Over-granular subtasks (death by API latency)
- Chain with no partial-result handling when step 2 fails

## Check questions

1. Nightly security review: “for every changed file, run the OWASP checklist, then write one summary.” Chain or adaptive? Why?
2. Why is “switch to a larger context window” the wrong fix for a patchy 14-file review?

## Connects to 1.7

Long chains and long investigations accumulate state. Resume, fork, or start fresh with a summary — that is 1.7.
