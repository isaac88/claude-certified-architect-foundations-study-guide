# 1.7 Session state, resumption, and forking

The Messages API is **stateless**. Every request must carry the history you still need. Claude Code and the Agent SDK add session helpers on top.

## Resume vs continue

| Flag | Behaviour |
|---|---|
| `--resume <name-or-id>` | Continue a **specific** named session |
| `--continue` | Continue the **most recent** session |

Name sessions that will span more than one sitting.

## Stale files and stale tools

The agent does **not** automatically know that files changed on disk since last time. When you resume, **tell it which files changed** and ask it to re-read them. Otherwise it reasons from cached understanding.

If prior **tool results** are stale (orders moved, code rewritten, APIs changed), **start a new session and inject a structured summary** of still-valid findings. Resuming replays outdated tool payloads as if they were current. The model cannot see the staleness.

| Resume | Fresh start + summary |
|---|---|
| Codebase mostly unchanged | Code or data significantly changed |
| Tool results still valid | Tool results outdated |
| Prior reasoning chain still useful | Only the conclusions matter; the chain is noise or wrong |

## `fork_session`

Same idea as 1.3: shared baseline, then independent branches (two test strategies, two refactors). Do not pay for the baseline twice.

## Hybrid memory (ties to Domain 5)

For long support chats, do not summarise the gold dust.

- **Case facts** (immutable): customer ID, verified order ID, disputed amount — kept at the top, never folded into a vague summary.
- **Rolling window:** last N turns.
- **Summary of the middle:** narrative only, no identifiers.

Progressive summarisation of amounts and dates is an exam trap.

## Instruction drift

In a 40-turn conversation the model starts ignoring “verify identity before refund”. That is drift, not a missing tool.

Mitigate with periodic re-injection of constraints (and still use a **hook** for the refund itself — 1.4/1.5. Drift is why prompts alone fail in long sessions).

## Identity ambiguity

Lookup returns five “John Smith”s. Never pick the first. Return an ambiguity error and ask for another identifier.
