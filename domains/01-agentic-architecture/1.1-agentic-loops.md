# 1.1 Agentic loops

An **agent** is not a one-shot chatbot. It is a loop: Claude decides an action, your code executes it, Claude sees the result, Claude decides again, until Claude signals it is finished.

Your code does not plan the steps. Your code runs the loop and obeys Claude’s signals.

## Production picture — order lookup

Customer: *“Where is my order ORD-8841?”*

Tools: `lookup_order`, `get_tracking`, `send_email`.

1. App sends the question to the **Messages API** with tool definitions.
2. Claude returns a `tool_use` block: `lookup_order(order_id="ORD-8841")`.
3. Your code hits the order service. Result: shipped, DHL, tracking `DHL-992`.
4. You **append** a user message of `tool_result` blocks. Send the full history back.
5. Claude calls `get_tracking("DHL-992")`.
6. You execute, append: out for delivery, ETA 16:00.
7. Claude writes the customer-facing answer. `stop_reason` is `end_turn`.
8. You present that answer. Loop over.

Multi-agent systems in 1.2 are this loop nested inside another loop.

## The contract: `stop_reason`

| `stop_reason` | Meaning | Your job |
|---|---|---|
| `"tool_use"` | Claude wants one or more tools run | Execute them, append `tool_result`s, call the API again |
| `"end_turn"` | Claude has finished | Show the final text |
| `"max_tokens"` / `"stop_sequence"` | Cut off | Not “done”. Handle as an incomplete turn |

A single assistant message can contain **both** `text` and `tool_use` blocks. Claude often says “I’ll look that up” *and* requests `lookup_order` in the same turn. Completion is decided by `stop_reason`, never by the type of `content[0]`.

## What you append, and why

Tool results go into conversation history as a new **user** message of `tool_result` blocks, each tied to the matching `tool_use_id`.

If you execute the tool but do not append the result, the next call has no new information. The model only reasons about what is in the message list.

```
user:        "Where is my order ORD-8841?"
assistant:   [text] + [tool_use lookup_order]
user:        [tool_result: shipped, DHL-992]
assistant:   [tool_use get_tracking]
user:        [tool_result: out for delivery, 16:00]
assistant:   "Your order is out for delivery around 16:00."
             stop_reason: end_turn
```

## Model-driven vs hardcoded trees

**Model-driven (agent):** Claude looks at the conversation and chooses the next tool. Lookup failed? It might ask for an email, or try another tool.

**Pre-configured decision tree (workflow):** your code always does `lookup_order` → `get_tracking` → reply. Faster and cheaper when the path is known. Useless when the next step depends on what you just learned.

The exam **favours model-driven** when the path is genuinely unknown. It **favours programmatic enforcement** when a business rule must never be skipped (1.4). Flexibility is not “the model can be trusted with refunds”.

## Exam traps

1. **Parse natural language to decide the loop is done.** “I’m done” is ambiguous. Claude can say that and still emit `tool_use`. `stop_reason` exists so you never do this.
2. **Arbitrary iteration caps as the primary stop.** “Stop after 10 loops” either cuts off useful work or burns empty turns. A cap is a **safety fuse**, not the completion condition.
3. **“If the response contains text, we’re done.”** Text routinely sits beside `tool_use` blocks.

## Practice scenario

A developer writes:

```python
response = client.messages.create(...)

if response.content[0].type == "text":
    return response.content[0].text  # treat as finished
else:
    # execute tools and loop
    ...
```

In production the agent **sometimes terminates prematurely**. The customer sees “Let me look that up for you.” and nothing happens.

**Bug:** the first content block is often `text` even when `stop_reason` is `tool_use`. The loop never executes the tools sitting in later blocks.

**Fix:** branch on `response.stop_reason`, not on `content[0].type`. On `"tool_use"`, execute every `tool_use` block in `content`, append results, iterate. On `"end_turn"`, return the text.

## Check questions

1. Why is “stop after 10 iterations” the wrong *primary* completion rule?
2. After `lookup_order` runs, what must you put into the next API request besides the new tool result?
